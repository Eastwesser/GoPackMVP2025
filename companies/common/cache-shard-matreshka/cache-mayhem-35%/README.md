# Руководство по работе с каналами в Go

## Текущая архитектура каналов

### В проекте используются три типа каналов:

#### 1. lineChan - буферизированный канал
```go
lineChan := make(chan LineMessage, len(allLines))
```
- Буфер: равен количеству строк в стихотворении (4)
- Назначение: передача строк от писателей к судье-королю
- Почему буферизированный: предотвращает блокировку поставщиков при временной перегрузке

#### 2. verdictChan - небуферизированный канал
```go
verdictChan := make(chan bool)
```
- Буфер: нет (синхронный)
- Назначение: передача вердикта от судьи-короля к главной горутине
- Почему небуферизированный: нужна синхронная передача результата

#### 3. stopChan - сигнальный канал
```go
stopChan := make(chan struct{})
```
- Буфер: нет
- Назначение: сигнал остановки для всех горутин
- Почему struct{}: минимальное потребление памяти, только сигнал

### Когда использовать буферизированные каналы?
✅ Использовать буферизацию когда:
- Писатель быстрее читателя - буфер смягчает временную нагрузку
- Несколько писателей - предотвращает блокировку
- Пакетная обработка - можно накапливать данные для обработки
- Rate limiting - ограничение скорости обработки

❌ Избегать буферизации когда:
- Нужна синхронность - гарантия immediate handoff
- Точное управление потоком - избежать накопления отложенной работы
- Сигнальные каналы - только для синхронизации

### Критические ошибки и их решение

### 🚨 PANIC "send on closed channel"

Причина: Попытка отправить в закрытый канал

Решение:
```go
select {
case <-stopChan:
return
case channel <- data:
// успешная отправка
case <-time.After(timeout):
// таймаут отправки
}
```

### 🚨 Deadlock

Причина: Все горутины заблокированы ожиданием каналов

Решение: Всегда использовать select с default или таймаутами

### 🚨 Горутины-зомби

Причина: Незавершенные горутины без механизма остановки

Решение: Использовать stopChan и defer wg.Done()

### Best Practices

- Всегда закрывайте каналы отправителем

- Используйте select для неблокирующих операций

- Сигнальные каналы делайте с chan struct{}

- Буферизация - только при необходимости

- Всегда используйте WaitGroup для ожидания горутин

### 📊 Анализ производительности:

#### 6 горутин на 6 строчек - хорошее соотношение, потому что:

- Параллелизм: Каждая горутина может работать на отдельном ядре CPU
- Баланс: Писатели успевают генерировать строки, а потребитель успевает их обрабатывать
- Буферизация: lineChan с буфером 6 идеально подходит для 6 строк

#### Что будет лучше? Зависит от задачи:

- Меньше строчек (4): Быстрее выполнение, выше процент успеха
- Больше горутин (8-12): Больше параллелизма, но возможна конкуренция

// Оптимальная настройка для большинства случаев

#### ⚠️ Важные предостережения:
```go
for i := 0; i < 1000; i++ { // ❌ Перегрузка планировщика
    go worker()
}

// ЛУЧШЕ: Ограниченный пул
semaphore := make(chan struct{}, runtime.NumCPU()*2)
for i := 0; i < 1000; i++ {
    semaphore <- struct{}{}
    go func() {
    defer func() { <-semaphore }()
    worker()
    }()
}
```
